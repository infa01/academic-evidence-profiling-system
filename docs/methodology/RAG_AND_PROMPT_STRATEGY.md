# RAG and Prompt Strategy

The project uses controlled retrieval-augmented generation (RAG) to produce
student-facing employability and career guidance from the final structured
academic evidence profile.

The LLM is not treated as the source of truth. It is used as a language
generation layer over retrieved evidence.

## Retrieval Design

The current implementation uses structured runtime retrieval rather than a
persistent vector database. The evidence base is the final structured student
profile generated by the pipeline, not a large external document corpus.

At generation time, the system converts the profile into evidence chunks,
embeds the chunks and retrieves the most relevant evidence for each predefined
report section. This avoids passing the entire JSON profile to the LLM as a
single context block and keeps the prompt auditable.

A persistent vector database would require indexing, embedding storage,
collection management, update handling and additional retrieval evaluation.
That design would be appropriate for a larger deployment with many students,
large document collections, uploaded CVs or open-ended user questions. For this
BSc prototype, runtime section-based retrieval is a smaller and more explainable
fit.

Future implementations could replace the runtime chunk store with FAISS,
Chroma, Qdrant or a similar vector database while keeping the same evidence
chunk schema and prompt quality contract.

## Generation Modes

The system supports two generation modes.

### Generic Employability Report

The generic report summarises the student's academic evidence profile:

- strongest ESCO skill evidence signals;
- semantic skill domains;
- ESCO occupation-orientation signals;
- CV-support wording;
- development areas and next actions;
- responsible interpretation.

### Targeted Occupation Advisor Report

The targeted report is generated for one selected ESCO occupation-orientation
signal. Retrieval is constrained to:

- the selected occupation;
- its supporting ESCO skills;
- matching calibrated skill evidence;
- methodology and limitation notes.

This mode supports evidence-based career reflection, CV positioning and
development planning. It does not produce a job recommendation.

## Prompt Structure

Prompts are generated from structured data and contain:

- system framing;
- methodology snapshot;
- selected mode;
- retrieved structured evidence;
- required output sections;
- forbidden claims;
- quality checklist.

The prompt instructs the model to avoid invented tools, projects, certifications,
work experience, grades or personal attributes.

The prompt also treats retrieved evidence and student/module text as data rather
than instructions. This is intended to reduce prompt-injection risk from text
that could appear inside inputs or retrieved chunks, such as instructions to
ignore previous rules or claim professional certifications.

## RAG Quality Contract

Each generation run records metadata:

- generation mode;
- selected model;
- prompt path;
- report path;
- retrieved evidence path;
- retrieval summary;
- required section checks;
- forbidden phrase checks;
- warning checks;
- quality gate status.

The quality gate is deterministic. It checks whether the report contains required
sections, avoids forbidden overclaims and was generated without warning markers.
It does not prove factual correctness, so human review remains required.

After generation, the generic and targeted reports also pass through deterministic
post-processing. This removes unexpected extra sections and softens wording that
could imply professional competence, job suitability or real work experience
rather than academic evidence. The post-processing step is part of the safety
contract; it does not add new evidence.

Prompt-injection resistance is therefore treated as a guardrail rather than a
complete security solution. Targeted generation selects an occupation from
existing ESCO orientation outputs instead of treating arbitrary free-form career
claims as ground truth.

## Automated RAG Evaluation

The repository includes `scripts/evaluate_rag_generation.py`, a lightweight
RAGAS-inspired evaluation script for the generated generic report. It does not
run the official RAGAS package and it does not replace expert validation.
Instead, it provides reproducible proxy metrics that align with common RAG
evaluation dimensions:

- context precision proxy;
- section relevance proxy;
- faithfulness proxy;
- answer relevance proxy;
- evidence mention coverage.

The distinction is important. RAGAS is a formal automated evaluation framework
for RAG systems, including metrics that examine whether retrieved context is
useful and whether the answer is faithful and relevant to the task (Es et al.,
2024). ARES is a heavier automated RAG evaluation framework that evaluates
context relevance, answer faithfulness and answer relevance using trained or
synthetic-data-supported judges (Saad-Falcon et al., 2023). The project script
does not reproduce those frameworks. It implements a small local approximation
of their evaluation dimensions using the same sentence-transformer family
already used by the pipeline.

This is why the output is described as proxy evaluation. It is useful for
diagnosing whether the local report is broadly grounded in retrieved evidence,
and it was used to refine the prompt and post-processing rules. It is not a
replacement for official RAGAS/ARES scoring, a judge-model benchmark or expert
career-advisor validation.

The script reads `output/employability_report.txt`,
`output/rag_retrieved_evidence.json` and `output/rag_generation_metadata.json`,
then writes:

```text
output/rag_evaluation_metrics.json
output/rag_evaluation_metrics.md
```

The evaluation was also used iteratively. An initial run identified generic
career-advice wording that was less directly supported by retrieved chunks. The
prompt was then tightened and deterministic post-processing was added. In the
final baseline run, context precision remained high, faithfulness reached 1.00
under the proxy metric and evidence mention coverage reached 1.00. These results
support the dissertation argument that RAG improves grounding, while still not
removing the need for human review.

## Responsible Output Framing

The LLM must describe:

- skills as academic evidence signals;
- occupations as ESCO orientation signals;
- scores as theoretical evidence-strength indicators;
- recommendations as development guidance.

It must not describe:

- professional competence certification;
- guaranteed employability;
- job suitability;
- automated hiring decisions;
- ATS bypass tactics.

## Thesis-Safe Interpretation

A suitable dissertation phrasing is:

> The system uses controlled RAG to constrain LLM generation to retrieved
> structured evidence from the final academic evidence profile. The generation
> process stores prompts, retrieved chunks and quality metadata for auditability.
> This supports transparent employability guidance while reducing, but not
> eliminating, the risk of hallucinated or overconfident output.
